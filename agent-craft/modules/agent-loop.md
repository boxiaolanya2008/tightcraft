# 工具编排与执行循环模块 — 让多步动作可控

## Boundary 硬边界

- 编排 = **带状态的执行循环**，不是线性脚本铺排。
- 每步一个可判定出口;失败必须有恢复或终止路径，不得无限重试。
- 所有副作用(写文件/网络/容器)在动作前后都有快照/回滚依据。
- 并发步骤只合并**相互独立**的动作；共享状态者串行。

## Teaching 执行循环最优做法

### 1. 执行状态机

```
计划 → 预检 → 执行 → 校验 → 记账
          ↑        │       │
          └────────┴── 校验失败 ─→ 恢复/终止
```

- **计划**:定步骤链与出口。
- **预检**:存在性/连通性可探测(TEST-PATH、HTTP 探针)，不靠报错探测。
- **执行**:单步原子、可回滚。
- **校验**:对比预期，判 pass/fail。
- **记账**:是否需重跑、是否新依赖，写入状态。

### 2. 步骤设计三要素
每一步写清:
- **入参契约**:上步输出与本步输入对齐。
- **出口判定**:可观察的 pass 标准(返回码/文件/响应字段)。
- **失败路径**:重试(n 次带退避)/降级/终止，三选一并写明条件。

### 3. 失败恢复策略

| 场景 | 处置 |
|---|---|
| 幂等副作用 | 安全重试(带 max_retries + 指数退避) |
| 非幂等副作用 | 终止/人工，不自动重试 |
| 前置环境缺失 | 先修前置，识别为不同根因，不归为重试 |

### 4. 副作用的可回滚
- 写文件先落版本/备份；改配置前导出当前文件。
- 渲染/生成视为可重建，后续可覆盖；外部注册操作视为需反向。

### 5. 原子提交
整个多步流程若需"全有或全无" → 分组为事务式提交；部分完成即中断不留半成品状态，或标记可续跑。

## Antipatterns 编排坏味道(源头规避)

- **线性铺排无状态** — 不看出口就接下一步。
- **无失败路径** — 只在成功后继续，失败即卡死。
- **盲目无限重试** — 同一动作高频重试，副作用重叠。
- **并行写共享状态** — 条件未独立就并发，竞态。
- **吞状态** — 前一步结果不传后一步契约，断链。
- **不留回滚依据** — 改前无快照，出错无法还原。

## Good Example

发布流程:build → test → package → release。
1. `build` 出口:产物存在且版本号匹配。
2. `test` 出口:CI 全绿，否则终止。
3. `package` 幂等(可重建)，失败带重试。
4. `release` 非幂等(标签/上传),失败即终止，人工接管。
5. 每步记账号，断点可续:
   `build ✓ → test ✓ → package ✓ → release ⏸`。

## Bad Example

一条长命令 `a && b && c && d`，任一失败静默退出无提示；失败后直接原样重跑导致重复标签/重复上传；未做快照，出错无法还原；并发跑互写同一配置文件。
