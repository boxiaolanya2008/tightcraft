# 安全重构模块 — 行为保持的意义变更

## Boundary 硬边界

- 重构 = **不改外部行为**，只改内部结构；任何行为变化都不是重构而是功能变更。
- 必配**安全网**:改动前有测试(或先补)，绿了才动。
- 一次一个语义单元；不顺手改无关代码、不"顺带格式化"。
- 契约不变:签名、返回结构、错误策略、边界面全保持。

## Teaching 重构最优做法

### 1. 先架安全网
- 为将被改动的函数补/跑用例，覆盖现行为(含边界与错误路径)。
- 无测试先补；克制的行为基准就是回归锚点。

### 2. 小步切换(seam)
每步用**可逆**的小改动(重命名→提函数→抽类→改实现)，每步可回滚。

### 3. 提取 vs 抽象纪律
- 提**重复**代码(真重复) → 提取。
- 不为"将来或许"建抽象；`ConfigManager` 包一个 dict 即过度。
- 抽象前问:去掉它是否还能写出来?能 → 直写。

### 4. 行为比对(改后通路)
- 改前跑一版行为基准；改后重跑同一基准，diff 必须为零。
- 输出格式/错误/时序若有差异 → 视为 regress，回退。
- 命名/类型变化处同步文档与调用方。

### 5. 缺陷重构与功能变更分流
- 发现 bug → 作为独立变更修，不与重构混在一个提交。

## Antipatterns 重构坏味道(源头规避)

- **无网裸改** — 没测试就大动，回归靠运气。
- **步幅过大** — 一次横跨数十处，出问题无法归因。
- **顺手改"顺手"** — 重构中塞样式/无关修复。
- **过度抽象/框架化** — 为假设需求建层，增加认知负担。
- **拖泥带水** — 遗留废弃变量、临时命名、死代码。

## Good Example

重复的 `fetch X` 提取为 `load_orders(user_id, status)`:
1. 补两处调用方行为用例(绿)。
2. 提函数，改名 `fetchData`→`load_orders`。
3. 重跑基准 → 输出一致。
4. 更新调用点与文档 → 回归全绿。
5. 交付，行为零漂移。

## Bad Example

无测试先动手；把三处逻辑并成一个巨型函数；顺手把 `user_id` 改名、删除注释、调整缩进；改到一半发现行为变了，无法回滚归因；遗留临时名 `x`。
